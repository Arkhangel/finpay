# RAG quality eval + Phoenix tracing (Б5.6)

Продолжение линии `docs/rag.md` (Б5.5, query pipeline с re-ranking и
цитатами) и `docs/chunking_experiment.md` (Б5.4, retrieval-метрики). Здесь —
пять метрик (Faithfulness/AnswerRelevancy/ContextPrecision/ContextRecall из
`ragas.metrics.collections` + `has_citation` через `@discrete_metric`),
Phoenix-трейсинг всего пайплайна (не только LLM-вызова), и два A/B
эксперимента поверх продакшен-конфигурации.

**Статус на 2026-07-25: golden dataset готов, baseline/A-B прогоны — нет.**
Причина — Groq исчерпал дневной лимит токенов (TPD) на продакшен-модели
`openai/gpt-oss-120b` во время генерации датасета; `RAGService.answer()`
использует ту же модель, так что реальный прогон оценки физически
невозможен до восстановления лимита (см. раздел «Ограничения» ниже). Разделы
с результатами ниже — заготовка, которая будет дополнена в следующей
сессии, как только лимит восстановится.

## Модели и почему именно так

| Роль | Модель | Провайдер | Почему |
|---|---|---|---|
| Продакшен-генерация (`RAGService.answer`) | `openai/gpt-oss-120b` | Groq | Действующий продакшен-конфиг (см. `docs/rag.md`) |
| Judge для RAGAS-метрик (`app/settings/eval.py: judge_model`) | `openai/gpt-oss-20b` | Groq | Намеренно ДРУГАЯ модель, чем продакшен — иначе модель оценивала бы сама себя. Изначально планировался `qwen/qwen3.6-27b` — не подошёл, см. баг №1 ниже |
| Генерация тестсета (`scripts/generate_testset.py --provider groq`) | `openai/gpt-oss-120b` (частично) / `openai/gpt-oss-20b` (после переключения) | Groq | Не судья и не участник оценки — конфликта интересов нет, поэтому можно совпадать с продакшен-моделью |
| Embeddings для AnswerRelevancy | self-hosted `intfloat/multilingual-e5-base` | локально | Тот же принцип, что и везде в проекте — не тащить OpenAI-эмбеддинги ради одной метрики |
| Tracing | Phoenix (`phoenix.otel.register`) + `OpenAIInstrumentor` + `LlamaIndexInstrumentor` | — | Второй инструментатор нужен, иначе retrieval/embedding-спаны не попадают в трейс — виден только сам LLM-вызов генерации |

### Отклонения от рекомендаций задания (осознанные)

Задание рекомендует конкретно `llm_factory("claude-sonnet-4-6", provider="anthropic",
client=AsyncAnthropic())` для judge и `OpenAIEmbeddings(client=AsyncOpenAI(),
model="text-embedding-3-small")` для AnswerRelevancy. Оба раза выбран
бесплатный self-hosted/Groq вариант вместо платного — тот же принцип, что и
в Б5.5 для продакшен-модели (см. `docs/rag.md`):

- **Judge**: `openai/gpt-oss-20b` (Groq) вместо `claude-sonnet-4-6` (Anthropic).
  Ключевое свойство — ДРУГАЯ модель, чем продакшен — сохранено; конкретный
  провайдер для этого свойства не важен. `anthropic>=0.40` поэтому не добавлен
  в группу `eval` в `pyproject.toml` (не используется).
- **Embeddings для AnswerRelevancy**: self-hosted `intfloat/multilingual-e5-base`
  вместо `text-embedding-3-small`. Та же self-hosted эмбеддинг-модель, что и
  для retrieval во всём проекте — не заводить отдельную OpenAI-зависимость
  ради одной метрики.

Оба отклонения не меняют методологию метрик (RAGAS считает их одинаково
независимо от того, чей LLM/embeddings API за ними стоит) — только источник
финансирования вызовов. Отмечено явно, чтобы на защите это звучало как
осознанный выбор, а не как «забыли выбрать модель из задания».

## Golden dataset (`tests/eval/golden_dataset.json`, 36 строк)

Задание рекомендовало сгенерировать датасет через RAGAS `TestsetGenerator`
целиком. На практике это не получилось сделать полностью за один день —
ниже честно, как собран итоговый набор и почему.

**4 строки — `source: "ragas"`.** Сгенерированы `TestsetGenerator` на
реальном корпусе `data/` (без `data/rag-block-03/` — отдельный исторический
корпус Б5.3/Б5.4). Прошли ручную проверку на язык (RAGAS выдал вопросы
преимущественно на английском для русскоязычного корпуса — см. баг №2) и
содержательность; включают как точечные вопросы, так и многошаговые
(«как связаны инцидент А и инцидент Б»).

**32 строки — `source: "manual"`.** Дописаны вручную из файлов `data/`,
которые RAGAS-батчи не успели затронуть (после offset 16 в
стратифицированном по категориям порядке файлов). Каждый `reference_contexts`
— дословная выдержка из документа (проверено программно: каждая строка
ручного контекста — точная подстрока полного текста корпуса после
нормализации пробелов), а не пересказ по памяти — иначе Faithfulness/
ContextRecall проверяли бы несуществующий контекст. Покрыты все 10 категорий
корпуса (api, compliance, incidents, integrations, legal, onboarding,
security, support, tariffs, webhooks); один вопрос («комиссия за
криптовалюту») — намеренный edge case вне базы, проверяет
score-guard-отказ (`REFUSAL_ANSWER` в `app/services/rag.py`).

### Баги, найденные при построении датасета

1. **Judge-модель `qwen/qwen3.6-27b` несовместима со structured-output
   RAGAS.** `ragas.metrics.collections` (используется в `app/eval/metrics.py`)
   строит judge через `ragas.llms.llm_factory(..., provider="openai",
   client=AsyncOpenAI(...))` — `provider="openai"` здесь означает
   «OpenAI-совместимый клиент по форме», не буквально OpenAI; сам клиент
   указывает на Groq через `base_url`. Эта фабрика жёстко использует
   Instructor `Mode.JSON` для структурированного вывода. `qwen/qwen3.6-27b`
   на каждый такой вызов возвращает Groq-ошибку `400 json_validate_failed`.
   `openai/gpt-oss-20b` (младший брат продакшен-модели, другие веса) работает
   стабильно, в том числе на русскоязычных промптах — проверено вживую.
2. **RAGAS генерирует персон и вопросы на английском по умолчанию,
   независимо от языка корпуса.** `ragas.testset.persona.PersonaGenerationPrompt`
   хардкодит `language="english"`. На первых 4 батчах (23 строки) 15 строк
   оказались на английском, 7 — смешанные, только 1 — чисто русская, хотя
   весь корпус `data/` на русском. Исправлено передачей вручную заданных
   `persona_list` (3 русскоязычные персоны — разработчик-интегратор, владелец
   бизнеса-мерчанта, специалист поддержки/комплаенс) в
   `TestsetGenerator.persona_list` — если он уже не `None`, RAGAS не вызывает
   LLM-автогенерацию персон вообще (заодно экономит несколько вызовов на
   батч). См. `scripts/generate_testset.py::_RU_PERSONAS`.
3. **`scripts/generate_testset.py --provider groq` изначально ломался на
   `ValueError: Unknown model 'openai/gpt-oss-120b'`.** Использовался
   `llama_index.llms.openai.OpenAI`, который валидирует `model` по
   захардкоженному списку официальных моделей OpenAI и отклоняет
   Groq-хостинг-модели даже с правильным `api_base`. Тот же баг уже был
   решён в `app/services/rag.py` через `llama_index.llms.openai_like.OpenAILike`
   — нужно было применить сразу, а не наступать на те же грабли повторно.
4. **`openinference-instrumentation-llama-index<4` несовместим с
   `llama-index-core==0.14.23`.** 3.x импортирует
   `llama_index.core.base.agent.types.{BaseAgent,BaseAgentWorker}` — модуль,
   которого в 0.14 уже нет. Ошибка (`ModuleNotFoundError`) всплывает только в
   момент вызова `LlamaIndexInstrumentor().instrument()`, а не при импорте —
   легко пропустить, если не проверить трейсинг вживую. Пин поднят до
   `>=4,<5` в `pyproject.toml`.
5. **Groq TPD (tokens per day) — жёсткий дневной лимит 200 000 токенов НА
   МОДЕЛЬ, отдельно от привычных RPM/TPM.** RPM/TPM видны в заголовках
   каждого ответа (`x-ratelimit-*`), TPD — только в теле ошибки `429` при
   реальном превышении, заранее остаток узнать нельзя. По накопленной
   статистике (347 успешных вызовов до первого `429` на `gpt-oss-120b`) —
   в среднем ~576 токенов/вызов, то есть лимита хватает примерно на
   3-3.5 полных батча генерации тестсета (при ~85-90 вызовов на батч из
   4 файлов). Лимит не сбрасывается заметными порциями в течение дня —
   похоже на скользящее 24-часовое окно, а не фиксированный сброс в
   полночь: значит, если исчерпать его, ждать восстановления в течение той
   же сессии бессмысленно.
6. **`has_citation` изначально была написана как regex-проверка (`\[\d+\]`),
   не LLM-судья — не по заданию.** Задание прямо требует `@discrete_metric`
   с промптом-судьёй, ловящим не только маркеры `[1]`/`[doc_id]`, но и
   текстовые формы ссылки («согласно …», упоминание имени файла) — regex это
   принципиально не может поймать. Переписано на `ragas.metrics.discrete_metric`
   с async-функцией, вызывающей `llm.agenerate(prompt, response_model=...)`
   (см. `app/eval/metrics.py::make_has_citation`). Проверено вживую на 3
   случаях: `[1]` → yes, «согласно нашей политике возвратов» → yes (то, что
   regex пропустил бы), без ссылки → no.
7. **`Faithfulness.ascore()` (и, вероятно, другие collections-метрики)
   иногда падают `json_validate_failed` на `gpt-oss-20b` без видимой связи
   с содержанием — не только на отказах.** Первый живой прогон
   `run_eval.py --label baseline` упал на первом же вопросе («Где вводить
   ИНН?») — score-guard сработал, `RAGService` вернул `REFUSAL_ANSWER`, и
   `StatementGeneratorPrompt` (первый шаг Faithfulness — разбивает ответ на
   атомарные утверждения) не смог получить валидный JSON на этом вырожденном
   входе (0 утверждений). **Гипотеза "только отказы" не подтвердилась**:
   второй прогон (после фикса ниже) упал на 6 строках подряд, из которых
   только 1 была реальным отказом — остальные 5 получили нормальные,
   уверенные ответы от продакшен-модели и всё равно не прошли Faithfulness.
   Похоже на общую флаки-совместимость `gpt-oss-20b`+Groq JSON-mode со
   схемой `List[str]` (`StatementGeneratorOutput.statements`), не привязанную
   к конкретному контенту. **Дополнительная находка:** Instructor (библиотека
   под капотом `ragas.llms.llm_factory`) по умолчанию `max_retries=1` —
   то есть НОЛЬ повторных попыток при сбое валидации; `ragas.llms.base`
   не прокидывает `max_retries` через `llm_factory(...)`/`InstructorModelArgs`
   наружу, так что штатно увеличить число попыток нельзя без правки ragas.
   **Решение:** `scripts/run_eval.py` оборачивает try/except ВСЮ строку
   целиком (и `RAGService.evaluate_inputs()`, и `eval_row()` — обе бьют по
   Groq и обе могут упасть), ошибка помечается в CSV (`error`) и не
   участвует в агрегатах `{label}_summary.json`, прогон продолжается на
   остальных строках. Не пытаться выдумывать эвристику вида "отказ =
   faithfulness 1.0" — это подмена измерения допущением, честнее просто
   считать такие строки `errors` и указать их долю в отчёте.
8. **Продакшен-модель `gpt-oss-120b` "восстановилась" лишь на бумаге —
   полтора часа спустя.** Маленький тестовый вызов (5 токенов) прошёл
   успешно — но полноценный прогон `run_eval.py` упал через несколько
   вопросов с той же ошибкой (`TPD Limit 200000, Used 199226`):
   восстановилось лишь несколько сотен токенов, не весь дневной бюджет.
   Маленький пинг — ложный признак готовности, не доказательство. **Ровно
   сутки спустя** (не полтора часа) реальный прогон `RAGService.answer()`
   отработал успешно — TPD действительно ведёт себя как ~24-часовое окно,
   как и предполагалось изначально в баге №5, просто требует терпения.
9. **`gpt-oss-20b` (judge) имеет всего 8000 токенов/минуту (TPM) — и одна
   строка golden dataset сама по себе может исчерпать это окно.** Faithfulness/
   ContextPrecision/ContextRecall видят `retrieved_contexts` целиком
   (~1500-2500 токенов/вызов при top-5 чанков), и 5 judge-вызовов на одну
   строку идут подряд без пауз — в реальном прогоне это почти всегда
   выжирало весь TPM-бюджет ДО того, как строка успевала завершиться, даже
   при `--concurrency 1` (то есть без единой конкуренции с другими
   вопросами — окно исчерпывала одна-единственная строка). Три подряд
   прогона `--label baseline` после снятия лимита gpt-oss-120b (баг №8)
   падали почти на 100% строк по этой причине, прежде чем разобрались.
   **Решение (первая итерация):** пауза `_METRIC_PACE_S` МЕЖДУ (не только
   ПОСЛЕ сбоя) вызовами метрик внутри `eval_row()` — 6с, потом 15с — не
   хватило: одна строка (5-6 judge-вызовов, Faithfulness внутри сама делает
   2) требует ~7000-8000+ токенов, то есть находится на грани бюджета вообще
   без всякой конкуренции.
10. **Retry на `json_validate_failed` сам оказался частью проблемы —
    "бесплатных" повторов не бывает.** TPM-429 — это отказ ДО генерации
    (токены не списываются, ретраить дёшево), а `json_validate_failed` —
    отказ ПОСЛЕ генерации (модель реально ответила невалидным JSON, токены
    списаны по-настоящему). Изначальный retry на 3 попытки не различал типы
    ошибок — каждая "повторная попытка" на content-сбое была на деле ещё
    одним платным вызовом, из-за чего собственные ретраи внутри одного
    прогона держали TPM-окно на нуле дольше, чем нужно (несколько прогонов
    подряд падали ~100% строк, "Used" в ошибках не двигался — see выше).
    **Решение:** `_ascore_with_retry` теперь различает типы ошибок — по
    наличию подсказки "try again in Xs" в тексте (rate-limit, дёшево) —
    до 3 попыток с паузой из подсказки; без неё (content-сбой, дорого) —
    изначально урезали до 1 повтора, см. баг №11 ниже, почему это оказалось
    неверным направлением. См. `app/eval/metrics.py::_METRIC_RETRIES_RATE_LIMIT`
    / `_METRIC_RETRIES_OTHER`.
11. **Ключевая находка: content-сбой (`json_validate_failed`) происходит
    ТОЛЬКО на `faithfulness`, ни разу на остальных 4 метриках.** Проверено
    по логам живого прогона: все 28 срабатываний `metric_retry` были
    `metric=faithfulness` — ни одного на `answer_relevancy`/
    `context_precision`/`context_recall`/`has_citation`. Логично: Faithfulness
    — единственная метрика с внутренним двухшаговым пайплайном (statement
    generation → NLI verification, см. `ragas.metrics.collections.faithfulness`),
    остальные — однократный вызов. Раньше `eval_row()` вызывала метрики
    последовательно и падение ЛЮБОЙ (то есть практически всегда —
    faithfulness) роняло ВСЮ строку — 4 рабочие метрики выбрасывались
    впустую из-за одной нестабильной. **Решение:** метрики в `eval_row()`
    считаются независимо (`_score_or_none`) — сбой одной даёт `None` только
    у неё, остальные 4 всё равно возвращаются. Заодно вернули
    `_METRIC_RETRIES_OTHER` с 1 до 4 повторов — раз сбой изолирован, можно
    себе позволить агрессивнее ретраить именно faithfulness, не рискуя
    столько раз впустую пересчитывать остальные 4. `{label}_summary.json`
    теперь включает `n_scored` (сколько из N строк реально досчиталось по
    каждой метрике) — если `faithfulness` даёт заметно меньше, чем
    `answer_relevancy`/`context_precision`/`context_recall`, это ожидаемо и
    не повод считать датасет/пайплайн сломанными.
12. **Настоящая причина, почему TPM-бюджет никогда не восстанавливался:
    `asyncio.Semaphore` в `scripts/run_eval.py` оборачивал только
    `evaluate_inputs()`, а не `eval_row()`.** Все предыдущие догадки (баг №9,
    пауза между метриками, разделение retry по типу ошибки) лечили симптом,
    не причину: `--concurrency 1` ограничивал только продакшен-вызов
    (`RAGService.answer`), а judge-вызовы (`eval_row`, вся нагрузка на
    `gpt-oss-20b`) уходили в `asyncio.gather` СОВСЕМ без ограничения — по
    факту judge одновременно обрабатывал все 36 строк датасета разом,
    независимо от значения `--concurrency`. Отсюда и стабильно нулевое
    восстановление TPM в логах ошибок (`Used` не падало от прогона к
    прогону) — это боролись не одна строка сама с собой, а весь датасет.
    **Решение:** `async with sem` расширен на оба вызова (`evaluate_inputs`
    И `eval_row`) внутри одного `try` — при `--concurrency 1` теперь
    действительно обрабатывается одна строка целиком, прежде чем начинается
    следующая. **Цена:** строка 1 после фикса прошла полностью чисто (первый
    раз за сессию), но заняла ~4.5 минуты (пауза между метриками + retry на
    faithfulness + внутренние вызовы AnswerRelevancy) — полный прогон на 36
    строк реалистично может занять 1.5-3 часа. Это осознанный компромисс
    (медленно, но надёжно), а не забытая оптимизация — см. также решение
    "растянуть baseline/A-B по дням" выше.
13. **Настоящая причина `json_validate_failed` на `faithfulness` (не "Groq
    иногда глючит", как думали сначала) — агрессивные дефолты сэмплинга.**
    Пользователь справедливо усомнился в объяснении "случайная нестабильность
    Groq" (0/4 успехов в реальном прогоне против моих 6/6 в ручном тесте) —
    и оказался прав. Разница: `InstructorModelArgs` по умолчанию ставит
    `temperature=0.01, top_p=0.1` — сам по себе этот факт не мешал бы, если
    бы `ragas.llms.base._map_openai_params()` корректировал их для
    "reasoning"-моделей (там принудительно `temperature=1.0`, без `top_p`) —
    но эта коррекция определяет модель через `model.startswith("gpt-")`, а
    наш model-id — `"openai/gpt-oss-20b"` (с префиксом `openai/`, как
    называет его Groq) — под этот префикс не подходит вообще, так что
    агрессивные дефолты остаются как есть. Живой тест это подтвердил:
    тот же system+user промпт с `temperature=0.01, top_p=0.1, max_tokens=1024`
    дал 2 сбоя из 4 попыток; без них — 0 из 6. **Решение:** `build_judge()`
    передаёт `temperature=0.2, top_p=1.0, max_tokens=2048` явно через
    `llm_factory(..., **kwargs)` (они доходят до `InstructorLLM.__init__`,
    который мержит kwargs поверх дефолтов `InstructorModelArgs`) — для ВСЕХ
    5 метрик, не только faithfulness (остальные 4 ни разу не падали и на
    дефолтных параметрах, но и вреда от более вменяемого сэмплинга для них
    быть не должно). Ещё не проверено на полном прогоне (см. баг №14).
14. **`scripts/run_eval.py` терял ВСЕ результаты при прерывании на
    середине — не только недосчитанное.** CSV писался одним куском в самом
    конце `main()`; если прогон падал на 429/TPD/Ctrl-C на строке 20 из 36
    (а после первого TPM-бага это буквально происходило несколько раз за
    сессию), 19 уже успешно посчитанных строк выбрасывались вместе с
    недосчитанными — токены на них потрачены впустую. **Решение:**
    построчная запись в `results/_wip_{label}.csv` сразу по готовности
    каждой строки (не дожидаясь конца прогона), плюс resume — повторный
    запуск с тем же `--label` подхватывает уже посчитанные вопросы из
    `_wip`-файла и досчитывает только недостающее; финальный
    `{timestamp}_{label}.csv` собирается из `_wip` в конце, после чего
    `_wip`-файл удаляется. Полная схема колонок (`_ROW_COLUMNS`)
    фиксирована и применяется к КАЖДОЙ строке (успешной и упавшей
    одинаково) — иначе построчный `pandas.to_csv(mode="a")` на строках с
    разным набором полей молча съезжает по колонкам (проверено вживую:
    `error` утекает в чужую колонку, если предыдущая успешная строка была
    длиннее).

## Ограничения (текущие, будут сняты в следующей сессии)

- **Продакшен-модель `openai/gpt-oss-120b` не имеет дневного бюджета Groq на
  момент завершения этой сессии.** `RAGService.answer()` (и, соответственно,
  `scripts/run_eval.py`, baseline, оба A/B эксперимента) не может быть
  реально прогнан, пока лимит не восстановится — ориентировочно нужно ждать
  порядка суток от момента, когда бюджет был исчерпан (не полночь по UTC, а
  скользящее окно, см. баг №5 выше). **Важно: маленький тестовый вызов (5
  токенов) может пройти успешно, даже когда реального бюджета почти нет** —
  проверено вживую: пинг прошёл, но первая же попытка `--label baseline`
  упала на 3-м вопросе с той же ошибкой `TPD Limit 200000, Used 199226` —
  значит, восстановилось лишь несколько сотен токенов, не весь лимит.
  **Не считать успешный маленький пинг доказательством, что можно гнать
  полный прогон** — проверять только полным прогоном, готовым остановиться
  на первой же 429.
- Датасет собран смешанным способом (RAGAS + ручные пары) — это прозрачно
  зафиксировано полем `source` в каждой строке и в `tests/eval/README.md`,
  но стоит иметь в виду при интерпретации результатов: RAGAS-строки
  (4 шт.) и ручные (32 шт.) могут иметь разное распределение сложности.
- **Одного восстановления дневного лимита Groq, скорее всего, не хватит на
  всё сразу.** Прикидка по токенам: один ответ `RAGService.answer()` на
  golden dataset — контекст до `rerank_top_n=5` чанков по `chunk_size=512` ≈
  2500-3000 токенов + промпт + ответ, то есть baseline (36 вопросов) сам по
  себе ≈ 90-125 тыс. токенов — больше половины дневных 200k на
  `gpt-oss-120b`. С judge-стороны ещё хуже: 5 метрик × 36 строк × 3 прогона
  (baseline + 2 A/B) = 540 judge-вызовов на `gpt-oss-20b`, каждый видит тот
  же тяжёлый `retrieved_contexts` — это может кратно превысить дневной
  бюджет судьи. **Решение: baseline и оба A/B эксперимента растягиваются на
  несколько дней (по одному прогону на восстановление лимита), не ужимается
  golden dataset и не режется набор метрик** — надёжность важнее скорости.
- **Docker/Qdrant недоступны в среде этой сессии** (`docker compose up` не
  проходит — демон недоступен), поэтому переиндексация для A/B-1 (см. ниже)
  подготовлена (команды проверены на подстановку переменных окружения), но
  не выполнена вживую. Выполнить нужно там, где Qdrant реально поднимается
  (`docker compose up -d qdrant`, см. `compose.yaml`).

## A/B эксперимент №1: chunking — semantic (прод) vs recursive/1024 (TODO)

Б5.4 (`docs/chunking_experiment.md`) уже сравнил fixed_size/recursive/semantic
на **retrieval**-метриках (chunk_size=512 у всех трёх) и выбрал semantic —
она и в проде (`chunking_strategy=semantic`). Тот вариант из задания
(`chunk_size 512→1024`) неприменим буквально: semantic не использует
`chunk_size`. Поэтому эксперимент — semantic (прод) vs alternative-стратегия
с `chunk_size=1024`, теперь на **generation**-метриках (Faithfulness и т.п.),
которые Б5.4 не мерил вообще.

**Важный нюанс, найденный при подготовке:** `scripts/ingest.py::_build_pipeline`
различает только `chunking_strategy == "semantic"` vs всё остальное — при
любом другом значении всегда берётся `SentenceSplitter(chunk_size,
chunk_overlap)` (эквивалент **recursive** из Б5.4), а не `TokenTextSplitter`
из `app/services/chunking.py::fixed_size()` (та функция используется только
в `scripts/chunking_experiment.py`, не в продакшен-индексации). Так что
сравнение по факту — semantic vs recursive/1024, не semantic vs fixed_size/1024.

**Переиндексация уже выполнена и проверена** (Docker/Qdrant поднялись в
рамках этой же сессии) — осталась только сама eval-часть, которая ждёт
Groq:

```bash
# 1. Переиндексировать корпус в ОТДЕЛЬНУЮ коллекцию с recursive/1024 —
#    отдельные kb_collection и docstore_path, чтобы не задеть прод.
RAG__KB_COLLECTION=finpay_kb_chunk1024 \
RAG__CHUNKING_STRATEGY=recursive \
RAG__CHUNK_SIZE=1024 \
RAG__CHUNK_OVERLAP=64 \
RAG__DOCSTORE_PATH=storage/docstore_kb_chunk1024.json \
python scripts/ingest.py data/

# 2. Прогнать eval на альтернативной коллекции (тот же golden dataset).
RAG__KB_COLLECTION=finpay_kb_chunk1024 \
python scripts/run_eval.py --label chunk_recursive_1024
```

**Статистика по чанкам (реальный прогон, без Groq):**

| Стратегия | Документов | Чанков | Чанков/документ |
|---|---|---|---|
| semantic (прод, `finpay_kb`) | 172 | 233 | 1.35 |
| recursive / chunk_size=1024 (`finpay_kb_chunk1024`) | 172 | 172 | 1.00 |

При `chunk_size=1024` подавляющее большинство документов корпуса (в среднем
~1000-1800 символов) укладываются в один чанк целиком — recursive/1024
практически не режет документы, тогда как semantic всё равно находит внутри
многих документов смысловые разрывы и делит их на 1-2+ части. Retrieval на
новой коллекции проверен вживую (`RAGService.retrieve()`, без LLM) —
работает корректно (пример: top_score 0.858 на вопросе про комиссию,
верно найден `02_tariffs.md`).
