# Итоговое описание решений (диплом)

Единый свод по формату «что выбрано → из чего выбиралось → почему» для всего
проекта. Детальные обоснования и цифры по каждому решению — в связанных
документах ниже; здесь — синтез для защиты, без повторного пересказа всех
деталей.

## 1. Задача и пользователь

FinPay — ассистент техподдержки платёжного процессинга. Пользователь —
мерчант или разработчик, интегрирующий FinPay (не конечный покупатель):
вопросы про тарифы/комиссии, статусы транзакций, возвраты, вебхуки, лимиты,
эскалацию инцидентов. Сценарии: (1) прямой вопрос по базе знаний с
цитированием источника, (2) многошаговый вопрос, требующий сопоставить
несколько документов, (3) действие с реальным внешним эффектом (уведомление
клиента) — только с подтверждением.

## 2. Почему здесь нужен ИИ

База знаний FinPay — не FAQ с десятком статичных вопросов, а ~22 документа
по 10 категориям (тарифы, безопасность, API, вебхуки, комплаенс и т.д.) с
пересекающимися и уточняющими друг друга условиями (например: базовая ставка
1.8%, но +1.0% для карт иностранной эмиссии, но -0.6% в льготный период для
новых мерчантов — три документа, один ответ). Поиск по ключевым словам или
статичная FAQ-страница не решает два реальных класса вопросов: (а)
перефразированные запросы без точного совпадения терминов, (б) вопросы,
требующие объединить факты из 2+ документов в одном ответе (см. находки Б6.5
ниже — именно эта декомпозиция и есть настоящая ценность LLM здесь, не сам
факт генерации текста).

## 3. База знаний

**Выбрано**: собственный markdown-корпус `data/<категория>/` (~22
документа, 10 категорий: tariffs, support, security, api, webhooks, legal,
compliance, onboarding, incidents, integrations), написанный вручную под
предметную область, не взят из открытого датасета.

**Из чего выбиралось**: (а) открытый FAQ-датасет по финтеху — не нашлось
адекватного русскоязычного аналога под конкретно платёжный процессинг с
нужной структурой категорий; (б) генерация корпуса LLM целиком — отклонено,
источник фактов должен быть проверяемым человеком, а не сгенерированным.

**Почему**: ручной корпус даёт контроль над фактической точностью (каждый
факт — не выдумка модели) и позволяет тестировать retrieval на честном
golden dataset с точно известными эталонными ответами (`tests/eval/golden_dataset.json`,
36 вопросов, вручную сверенных на дословное совпадение с корпусом —
`docs/rag_evaluation.md`).

## 4. Архитектура

Схема компонентов — README.md (раздел «Архитектура», mermaid), детальный ADR
по паттерну взаимодействия — `docs/architecture.md`. Путь запроса: клиент
(Telegram/REST) → модерация входа → `ChatService` (история + sliding window
контекст) → RAG-retrieval (Qdrant → re-ranker → score-guard) ИЛИ агентный
граф (LangGraph, tool calling + HIL) → LLM (Groq) → ответ с цитированием →
Postgres (история + чекпоинты агента) + Redis (кеш ответов) + Phoenix
(трейсинг).

**Честная оговорка**: `docs/architecture.md` (ADR-001, ранний этап проекта)
фиксирует выбор Request-Response вместо Streaming — это решение с тех пор
устарело: чат (`POST /chats/{id}/messages`) и агент (`POST /agent/stream`)
оба реализованы как SSE-стриминг в более поздних блоках курса (М4, Б6.4).
ADR-001 оставлен как исторический документ выбора на момент М3, а не как
описание текущего поведения — README.md отражает актуальное состояние.

## 5. Выбор модели

**Выбрано**: облачная модель через Groq (`openai/gpt-oss-120b`,
OpenAI-совместимый API) для генерации и агента; embedding-модель — **локальная**,
self-hosted `intfloat/multilingual-e5-base` (sentence-transformers, CPU).

**Из чего выбиралось**: для генерации — платный OpenAI (`gpt-5.4-mini`,
рекомендация заданий курса) vs Groq (бесплатный тариф, разные open-weight
модели) vs полностью локальный inference (Ollama). Для эмбеддингов —
платный OpenAI `text-embedding-3-small` vs self-hosted E5.

**Почему Groq, а не OpenAI**: осознанное отклонение от рекомендаций заданий
на всём протяжении курса — нулевая стоимость на объёме учебного проекта,
приемлемое качество для support-домена. Плата за это — реальные найденные
баги от более слабых моделей (см. `docs/rag_evaluation.md`, `docs/rag.md`
раздел про синтез по 3+ источникам) и Groq-специфичные ограничения по
дневной квоте (TPD), из-за которых RAG-эвал не доведён до конца (раздел 9).
Модель внутри Groq менялась дважды за курс из-за депрекации
(`llama-3.1-8b-instant`/`llama-3.3-70b-versatile` → `openai/gpt-oss-120b`,
2026-07-25) — реальный операционный риск бесплатного тарифа, не
гипотетический.

**Почему не полностью локальный inference**: оценивался вживую (см. диалог
в ходе Б6.4/6.5) — `gpt-oss-120b` локально требует ~60-70GB+ весов даже в
квантованном виде, что на обычном десктопе без датацентрового GPU выливается
в кратно более медленный инференс (минуты вместо секунд на ответ), особенно
критично для ReAct-циклов с несколькими LLM-вызовами на шаг. Локальная
модель меньшего размера (~20-30B) была бы по классу сопоставима с уже
используемой судейской моделью (`openai/gpt-oss-20b`), которая на практике
показала себя ненадёжной именно в роли строгого structured-output судьи
(`docs/rag_evaluation.md`) — снижение размера модели создаёт реальный риск
качества, не только риск скорости.

**Почему self-hosted эмбеддинги, а не OpenAI**: текст обращений (потенциально
чувствительные данные мерчантов) не должен уходить во внешний API просто для
получения вектора — self-hosted устраняет этот риск полностью и
бесплатен (`ADR-003`, `docs/architecture.md`).

## 6. Хранение и поиск

**Выбрано**: Qdrant (векторная база), метрика cosine, чанкинг —
`semantic`-стратегия (LlamaIndex `SemanticSplitterNodeParser`), re-ranking
включён (`BAAI/bge-reranker-v2-m3`), top-k=10 → top-n=5 после re-rank.

**Из чего выбиралось**: чанкинг — `fixed_size` / `recursive` / `semantic`
(grid search на golden dataset, `docs/chunking_experiment.md`); метрика
Qdrant — cosine vs dot (`docs/vector_store.md`, `scripts/qdrant_experiments.py`
подтвердил идентичное ранжирование на нормализованных векторах, cosine выбран
как более явный/читаемый вариант); re-ranker — включать/выключать
(`docs/rag.md` — обоснование).

**Почему**: `semantic` дал лучший MRR@10 (0.917) при равном Hit Rate/Recall
на 10-документном корпусе Б5.4; re-ranker включён при переходе к более
крупному (~22 документа, 10 категорий) корпусу Б5.5, где грубый similarity
retrieval уже недостаточен. Порог отказа (`score_threshold=0.005`) —
откалиброван на реальных score cross-encoder'а ПОСЛЕ re-ranking (несопоставим
с косинусной шкалой до re-ranking) — подробный разбор ограничений порога
(намеренно низкий, второй слой защиты — промпт "не выдумывай факты") — `docs/rag.md`.

## 7. Агентный слой

**Выбрано**: single-agent с tools (LangGraph `StateGraph`, персистентный
чекпоинтер + human-in-the-loop) — `app/services/agent_persistent.py`.

**Из чего выбиралось**: пройдена полная прогрессия от голого tool-calling
цикла (Б6.1) через ReAct+self-reflection (Б6.2) до LangGraph (Б6.3), и
отдельно — supervisor-мультиагент (researcher+writer, Б6.5) как альтернатива
single-agent на том же наборе задач.

**Почему single-agent, а не мультиагент**: реальное сравнение на 5
одинаковых вопросах (`experiments/`, `docs/multi-agent-report.md`) — качество
не выросло в среднем (4.4/5 у обоих), стоимость выросла в 8.6× по токенам и
29.9× по медианной задержке; на тривиальном вопросе координация улетела в 25
LLM-вызовов и ответ вышел на английском вместо русского. Домен FinPay — общий
узкий контекст (2-3 связанных документа на большинство вопросов), а не
breadth-first research, где мультиагент по данным Anthropic реально
окупается. Единственный вопрос, где мультиагент содержательно выиграл
(многошаговый), дешевле закрыть промптом single-agent'а ("вызови tool
отдельно для каждой части вопроса"), чем целым слоем координации.

**Инструменты**: `search_knowledge_base` (RAG), `get_current_time`,
`send_telegram_message` — последний единственный опасный (реальный внешний
side-effect), поэтому единственный, требующий HIL-подтверждения
(`interrupt()`+`Command(resume=...)`, Б6.4) — idempotent-подготовка (`prepare_send_telegram`)
отделена от самого side-effect (`confirm_and_execute_send_telegram`) отдельным
узлом графа, чтобы resume не мог случайно продублировать отправку.

## 8. Поведение при сбоях

**Реализовано фактически** (не путать с ранним ADR-002 из `docs/architecture.md`,
который описывает circuit breaker + OpenAI-fallback — этот план не был
реализован в коде, `aiobreaker` в проекте не используется и провайдер один):

- Redis недоступен при старте → кеш отключается, сервис поднимается без
  падения (`app/lifespan.py`).
- Qdrant недоступен при старте → RAG/поиск отключается, приложение
  продолжает работать без него.
- RAG-сервис не может собраться → `/rag/query` и RAG-в-чате отключены,
  остальной чат работает.
- Groq API недоступен во время запроса → ошибка пробрасывается конкретному
  запросу (retry — только встроенный в OpenAI SDK, `max_retries=3`), без
  автоматического переключения на другого провайдера.
- Модерация/RAG-retrieve падают на конкретном сообщении → перехватываются
  точечно, не роняют весь чат (`app/chat/service.py`).
- Диалог и состояние агента переживают рестарт контейнера — Postgres
  (чат-история) и чекпоинтер (`AsyncPostgresSaver`, Б6.4) персистентны.

**Честно**: единой стратегии multi-provider failover нет — при полном отказе
Groq сервис отвечает ошибками на LLM-зависимые запросы, а не переключается на
запасной провайдер. Для учебного проекта с одним бесплатным провайдером это
принятый риск, не забытая работа — задокументирован явно.

## 9. Результат: как проверялось качество

Три независимых слоя проверки:

1. **RAG quality (RAGAS)** — `tests/eval/golden_dataset.json` (36 вопросов) +
   `scripts/run_eval.py` (Faithfulness/AnswerRelevancy/ContextPrecision/
   ContextRecall/`has_citation`, судья — отдельная от прод модель). **Не
   завершено**: 12/36 строк с реальными числами (faithfulness=0.756,
   answer_relevancy=0.785, context_precision=0.967, context_recall=0.889,
   citation_rate=0.667), оба A/B-эксперимента (chunking, reranker on/off)
   подготовлены, но не прогнаны — упирались в дневную квоту Groq, не в
   технические ограничения пайплайна (14 реальных багов найдено и
   исправлено по ходу, `docs/rag_evaluation.md`).
2. **Агентный слой** — реальные live-прогоны на всех этапах (Б6.1-6.4):
   численные метрики (токены/latency/итерации) на реальных задачах,
   найденные баги описаны с конкретными сценариями воспроизведения
   (`docs/agent-react-report.md`, `docs/agent-graph-report.md`,
   `docs/agent-persistent-report.md`).
3. **Мультиагент vs single-agent** — 5 вопросов × 2 реализации, реальные
   числа, ручная сверка качества с корпусом (`docs/multi-agent-report.md`).
4. **Security** — garak, baseline vs after security-слоя (`docs/security/`).

## 10. Ограничения и планы

См. README.md, раздел «Ограничения и известные пробелы» — синхронизировано,
не дублируется здесь. Ключевое: RAG-эвал не завершён (квота, не архитектура),
мультиагент сознательно не используется, единой стратегии failover между
LLM-провайдерами нет, coordination overhead агента не имеет бюджетного гарда.
