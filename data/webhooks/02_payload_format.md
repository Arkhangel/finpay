# Формат payload вебхуков FinPay

## Общая структура
Каждый вебхук — POST-запрос с JSON-телом вида:
```
{
  "event_id": "evt_8f3a...",
  "event_type": "payment.succeeded",
  "created_at": "2026-06-01T12:00:00Z",
  "data": { ... }
}
```
Поле `data` содержит объект, специфичный для типа события (например, для
`payment.succeeded` — полный объект платежа с суммой, валютой, статусом,
идентификатором мерчанта).

## Заголовки запроса
- `Content-Type: application/json`
- `X-FinPay-Signature` — HMAC-подпись тела запроса (см.
  `data/webhooks/04_signature_rotation.html`).
- `X-FinPay-Event-Id` — дублирует `event_id` из тела, для удобства
  фильтрации на уровне reverse-proxy/логов до разбора JSON.

## Ожидаемый ответ от получателя
Endpoint мерчанта должен ответить кодом `2xx` в течение 10 секунд. Тело
ответа не анализируется — важен только HTTP-статус. Любой код вне диапазона
2xx или таймаут более 10 секунд считается неуспешной доставкой и запускает
повторные попытки.

## Ограничение размера payload
Максимальный размер тела вебхука — 256 КБ. Для событий с большими
вложенными объектами (например, `payout.succeeded` с детализацией по
множеству транзакций) вложенный список обрезается до 100 записей, полный
список доступен через отдельный GET-запрос по ссылке в поле
`data.details_url`.

## Порядок доставки
FinPay не гарантирует строгий порядок доставки вебхуков между разными
event_id — например, `payment.succeeded` может прийти до или после связанного
`payout.created`, если они были инициированы почти одновременно. Логику
обработки нельзя строить на предположении о порядке, нужно ориентироваться
на `created_at` и текущий статус сущности через API.
