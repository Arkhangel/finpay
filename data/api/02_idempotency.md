# Идемпотентность запросов к API FinPay

## Зачем нужна идемпотентность
При таймауте или обрыве соединения интеграция не знает, был ли платёж
фактически создан на стороне FinPay. Повторная отправка того же запроса без
идемпотентности могла бы создать дублирующий платёж и списать с клиента
деньги дважды.

## Использование Idempotency-Key
Каждый POST-запрос на создание платежа должен содержать заголовок
`Idempotency-Key` — произвольную уникальную строку (рекомендуется UUID v4),
сгенерированную на стороне интеграции один раз для конкретной попытки оплаты.
При повторной отправке запроса с тем же ключом и тем же телом FinPay вернёт
результат первого запроса, не создавая новый платёж.

## Срок жизни ключа
Ключ идемпотентности действителен 24 часа с момента первого использования.
После истечения этого срока повторный запрос с тем же ключом будет
обработан как новый — создание дублирующего платежа в этом случае уже не
блокируется автоматически.

## Конфликт при разном теле запроса
Если запрос с уже использованным `Idempotency-Key`, но другим телом
(например, изменилась сумма) — FinPay вернёт `422 Unprocessable Entity` с
кодом ошибки `idempotency_key_conflict`, платёж создан не будет.

## Идемпотентность и вебхуки
Идемпотентность запроса на создание платежа не отменяет необходимости
проверять дубликаты вебхуков на стороне интеграции — вебхук об одном и том
же событии теоретически может быть доставлен более одного раза (см.
`data/webhooks/01_event_types.md`), обработчик должен быть устойчив к
повторной доставке независимо от Idempotency-Key запроса создания платежа.
